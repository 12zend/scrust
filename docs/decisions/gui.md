# GUI: TurboWarp's scratch-gui in Electron, projects run natively

`gui/` wraps TurboWarp/scratch-gui (vendored as plain files in `gui/vendor/scratch-gui`, upstream commit noted in `gui/scripts/setup.js`) in Electron. The GUI's imports of `scratch-vm` and `scratch-render` are aliased by `gui/webpack.config.js` to `gui/packages/scrust-vm` and `gui/packages/scrust-render`; the GUI's source is not patched. No WebAssembly is involved.

**Running.** The green flag saves the project as sb3; the Electron main process runs `scrust check` (to list unsupported blocks, which become no-ops) and `scrust build` (native, release). The executable is started as a child process with `--embed` (`crates/scrust-player/src/embed.rs`): no window; input arrives as text lines on stdin; the running-thread count and state snapshots leave as length-prefixed messages on stdout, which the main process forwards to the page. Frames (RGBA, only when the picture changed) are published in a shared memory file (`--frames-shm`, `crates/scrust-render/src/frames.rs`: two slots, each a seqlock) that the page reads with the renderer addon (`frame(path, seen)`) once per animation frame and draws on the stage canvas, so a frame is never copied through a pipe, the main process or IPC, and frames the page had no time for are skipped. Without the addon, frames go over stdout instead and the main process keeps at most one in flight to the page. Sound plays in the child process (rodio). The generated crate always has the same name (`gui_project`), so after the first build cargo only recompiles the project crate (a few seconds for the demo).

**Editing.** scrust has no editor model (PRODUCT.md §1.3). The block containers fed by Blockly events, targets, costumes, the extension and toolbox metadata and sb3 serialisation still come from scratch-vm's classes (`ScrustVM extends VirtualMachine`), but no script ever runs on scratch-vm or TurboWarp's JS compiler: `startHats`, `toggleScript` and `addMonitorScript` do nothing, `stepThreads` returns at once, threads that get pushed anyway are killed immediately, and the compiler option is forced off. Monitor values, normally produced by monitor threads, are read from the editor model.

**Drawing the editor.** `scratch-render`'s object model (skins, drawables, layer groups, pick, bounds, fencing, the drag image, the colour picker) is implemented by `scrust_render::Scene`, which shares the transform, sampler, effects and compositor with the player's `SoftRenderer`. The page reaches it synchronously through a Node-API addon (`crates/scrust-node`, loaded by the Electron preload; the Node-API functions are declared by hand, so there are no extra crates). Synchronous calls are required: scratch-vm measures a skin right after creating it. On macOS the scene, like the running program, draws with Metal (see `rendering.md`).

**After a run.** When the program stops or its last thread ends, it reports a state snapshot (`crates/scrust-player/src/state.rs`) and the GUI copies positions, directions, sizes, visibility, costumes, layer order, variables, lists and monitor visibility into the editor model, as Scratch leaves the project after a run. The last frame stays on the stage (including the pen layer) until the project is edited. Edits made while the program runs take effect at the next green flag, which recompiles.

**Browser version.** `gui/web` builds the same bundle for a plain browser (`npm run build:web`, output `gui/build-web`). The two bridges the Electron preload provides are replaced with browser implementations of the same interfaces (`gui/web/bridge.js`), so `packages/scrust-vm` and `packages/scrust-render` are unchanged: the editor's scene is `scrust_render::Scene` compiled to wasm32 (`crates/scrust-scene-wasm`, plain exports, arguments passed through an input buffer), and the green flag posts the sb3 to `gui/web/server.js`, which runs `scrust check` and `scrust build --target wasm` and returns the module. The program runs in the page on the web host (`crates/scrust-player/src/web.rs`), stepped once per animation frame; the embed protocol's input lines are translated to its exports, and its thread count and state snapshots (`scrust_threads`, `scrust_state`) produce the same messages as the native embed host. rustc cannot run in a browser, so compiling needs the server; it listens on 127.0.0.1 unless told otherwise. Sound plays with Web Audio as in the standalone web page; the first compile of a session builds the runtime crates for wasm32 and takes longer.

**Not supported.** Clicking a script to run it alone (the whole project is compiled), dragging sprites on the stage while a compiled program is shown, pen and speech bubbles in the editor view (they exist only in the running program), video sensing and other extensions scrust does not compile, Windows (the addon is linked for macOS and Linux only), SVG measurement as in scratch-svg-renderer (the document size is used, see `rendering.md`).
