# An IR interpreter for the browser

The GUI's browser build must run projects without anything outside the page (no compile server: people open it from a static host and cannot be expected to run one), and rustc cannot run in a browser. So `crates/scrust-interp` runs a project from its IR instead of generating Rust: the front end (sb3 loading, lowering, analysis), the runtime, the renderer and the interpreter are all ordinary Rust and compile to one wasm32 module (`scrust-interp.wasm`).

**Same behaviour as compiled code.** The interpreter mirrors `scrust-codegen` statement for statement in its `--no-unbox` form: every variable and list item is a dynamic `Value`, each IR node makes the same runtime calls in the same order (inputs in their recorded evaluation order, `pick random` between equal literals folded, an empty boolean slot false, the short-circuit of `and` / `or`), and threads suspend exactly where generated code has an `.await`. Where that is decided from the analysis (`stmt_may_yield`, `yields`, `callee_warp`, `promise_tail`), the interpreter asks the same analysis, so loop yields, warp mode, recursion yields and the skip-loop-yield flag cannot drift apart. Like the generator it has a synchronous half (functions that never suspend run with `&mut World`, without futures) and an asynchronous half (the thread futures the scheduler polls). `scrust trace --interp` runs it natively; `conformance/harness/run.js --ref compiled --mode interp` compares its traces with compiled programs byte for byte (all cases and the fuzzer).

**Run-time program definitions.** The runtime's script entry points (`ScriptDef::start`, `pred`, `SpriteDef::new_locals`) are boxed closures (`Send + Sync`, as skins are loaded on several threads) rather than function pointers, so a `ProgramDef` can be built at run time; generated code boxes its functions. The interpreter's closures carry only indices and find the IR through a thread-local. Names and asset bytes are leaked into `&'static` data as generated code has them; in the browser every run uses a fresh module instance, so nothing accumulates.

**Shared front end.** `scrust_codegen::frontend` (load, lower, analyse; unsupported-block report; TurboWarp frame rate), `created_on_compile` and `monitor_info` are used by both the compiler and the interpreter.

**Cost.** Interpreting is slower than compiled code (no unboxing, no inlining, a boxed future per asynchronous block); the native compiler and the Electron GUI are unchanged and remain the fast path.
